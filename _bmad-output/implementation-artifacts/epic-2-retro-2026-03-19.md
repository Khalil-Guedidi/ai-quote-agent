## What Went Well

### 1. Pipeline Architecture Held Through 6 Stories

The `received → cleaned → extracted → split` pipeline was designed in Story 2.1 and survived all 6 stories without refactoring. The inline integration pattern (processing within `_persist_emails()`) scaled cleanly from cleaning (pure CPU) to extraction (async LLM) to splitting (async LLM).

### 2. `with_structured_output()` Pattern

Established in Story 2.3 for LLM extraction, reused identically in Story 2.4 for splitting. Guaranteed schema-conformant output via Pydantic models — no manual JSON parsing. Became the team standard for LLM interactions.

### 3. Zero Regressions Across 120 New Tests

Every story added tests without breaking existing ones. Test count grew organically: 68 (Epic 1) → 91 → 110 → 125 → 139 → 164 → 188. Quality gates (mypy strict, ruff) prevented structural drift.

### 4. Clean Code Reviews

Reviews were smooth — mostly MEDIUM and LOW issues. No rejections, no major rewrites. The patterns established in Epic 1 (adapter, asyncio.to_thread, conftest helpers) reduced review friction significantly.

### 5. Security Layers Well-Separated

- `security/sanitizer.py` — prompt injection pattern detection and escaping
- `security/input_isolation.py` — delimiter-based structural separation
- `security/log_redactor.py` — confidential data redaction in logs
- `audit/logger.py` — JSON structured logging with automatic redaction

Each module has clear boundaries. Cleaning ≠ sanitization ≠ redaction.

### 6. Epic 1 Investment Paid Off

The adapter pattern, quality gates, health check extensibility, and async patterns from Epic 1 were reused without friction throughout Epic 2.

## Lessons Learned

1. **A project is a behavior, not a pile of code** — unit tests with mocks validate implementation, not behavior. E2E tests with real services are non-negotiable for epic validation.
2. **Untracked action items disappear** — if it's not a story in sprint-status, it doesn't exist. Proven twice across two retrospectives.
3. **Centralize project context** — `project-context.md` prevents each story from rediscovering the same pitfalls. The dev agent needs a single source of truth for conventions and known traps.
4. **Adversarial code review catches what unit tests miss** — all 3 HIGH issues (severity_max, recursive logging, regex over-matching) were found by review, not tests.
5. **Inline integration scales** — the pattern of processing within `_persist_emails()` (cleaning → extraction → splitting) held through 4 stories without refactoring.
6. **`with_structured_output()` is the LLM standard** — guaranteed Pydantic-conformant output, no JSON parsing, reusable across use cases.
7. **Security layers must be separate modules** — sanitization ≠ cleaning ≠ redaction. Each has its own domain and responsibility.
8. **Epic 1 quality investment compounds** — patterns established early (adapter, async, conftest) reduced friction in every subsequent story.

## Established Patterns (Carry Forward)

### Pipeline Integration Pattern
```
_persist_emails():
  for each email:
    persist → clean (inline, <1ms) → extract (async LLM) → split (async LLM)
    status: received → cleaned → extracted → split
    per-step error handling, never blocks pipeline
```

### LLM Structured Output Pattern
```python
model = adapter.get_model("simple")
structured = model.with_structured_output(PydanticModel)
result = await asyncio.wait_for(structured.ainvoke(messages), timeout=10.0)
```
