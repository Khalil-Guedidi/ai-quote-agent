## What Didn't Go Well

### 1. Story 3.6 Jargon Dictionary = Regression on "Zero-Preprocessing" Vision

The architecture explicitly states: "No synonym database or external dictionary — semantic understanding via BGE-M3 handles jargon natively." Yet Story 3.6 introduced a configurable abbreviation expansion dictionary (10 entries: inox, Ø, lg, DN, PN, etc.) — essentially a synonym table that will grow over time and require maintenance.

**Khalil's verdict:** "C'est une régression sur la vision produit. On a eu la même problématique sur le pipeline d'ArcelorMittal. Le but de ce projet était de résoudre ces problématiques, pas les réimplémenter avec une autre casquette."

This is the most significant finding of this retrospective.

### 2. CI/CD Pipeline Broken — Third Retrospective in a Row

The GitHub Actions pipeline fails on push. Nobody has investigated why. This was Action Item #1 from the Epic 1 retrospective ("PostgreSQL service container in CI"), marked ❌ in Epic 2 retro, and still unresolved. Three epics of development with no automated validation on push.

### 3. No Manually Testable Flow — Project Lead Is Blind

After 3 technical epics, the Project Lead has never seen the system execute. No CLI command, no API endpoint, no demo. 363 tests pass in local, but Khalil cannot run a search and judge the results. The jargon dictionary regression went unnoticed precisely because of this blindness.

### 4. Dead Code Persists (Reduced but Not Eliminated)

- Story 3.4: dead `log_proposability_filter()` function (SQL-level filtering makes pre/post counts unavailable)
- Story 3.0c: `sys.path` hack in test file (moved to conftest during review)

Pattern reduced from Epic 2 (3/6 stories) but still present. The dev agent leaves traces of its iterations.

### 5. asyncpg Limitations Not Anticipated

Story 3.3 discovered two asyncpg limitations:
- No concurrent queries on the same connection → `asyncio.gather()` replaced with sequential execution
- No parameterized `SET LOCAL` → f-string with `int()` cast for safety

The architecture assumed parallel search execution. A spike before design would have caught this.

### 6. Code Review HIGH Issues Not Caught by Tests

Story 3.5 had 2 HIGH issues:
- H-1: Missing commit after cache invalidation in `ingest_full()` — data integrity risk
- H-2: Search method absent from cache key — cross-method cache collisions

Both caught by adversarial code review, not by automated tests. Confirms Epic 2 lesson: "adversarial code review catches what unit tests miss."

## Lessons Learned

1. **Foundation stories retro-driven work** — proven across 2 epics now. 3.0a/b/c secured Epic 3 like they'll secure Epic 4 with 4.0a/b/c. The pattern is established.
2. **The Project Lead must see the product** — 3 epics without a manually testable flow = invisible regressions. The jargon dictionary regression is proof. Non-negotiable for Epic 4.
3. **CI/CD broken for 3 retros = systemic failure** — action items that aren't tracked as stories get lost. CI/CD must be a blocking story, not an action item.
4. **Don't reimplement the problem you're solving** — the jargon dictionary is the exact manual synonym maintenance pattern that the project exists to eliminate. Architecture decisions must be enforced during story creation, not just documented.
5. **Adversarial code review remains safety net #1** — all HIGH issues (cache key collision, missing commit) found by review, not tests. Continue investing in review quality.
6. **Spike before architecture assumptions** — asyncpg concurrency was assumed, not validated. A 30-minute spike would have saved redesign time in Story 3.3.
7. **SQL-level filtering > Python post-filtering** — proposability filter (Story 3.4) applied as WHERE clauses = correct LIMIT behavior + better performance. Pattern to carry forward.
8. **Tracking action items as stories works** — 4/5 completed (vs 2/6 in Epic 2). The process improvement is proven and should continue.

## Significant Discoveries — Epic 4 Impact

### Discovery 1: Project Lead Has No Visibility on System Behavior

After 3 technical epics, no manually testable flow exists. The Project Lead validates on trust, not observation. For Epic 4 (LLM reasoning, confidence scoring), this is unacceptable — reasoning quality requires human judgment.

**Action:** New Story 4.0b — CLI flux testable search. Blocker for all Epic 4 stories.

### Discovery 2: CI/CD Broken Since Epic 1

Third consecutive retrospective flagging this issue. 363 tests run only locally. No automated validation on push. With Epic 4 introducing non-deterministic LLM reasoning, silent regression risk is extreme.

**Action:** New Story 4.0a — Fix CI/CD pipeline. Blocker for all Epic 4 stories.

### Discovery 3: Story 3.6 Contradicts Product Vision

The jargon dictionary is a synonym table — the exact pattern the project was designed to eliminate. If not resolved, Epic 4 may lean on the dictionary as a crutch instead of pushing semantic understanding.

**Action:** New Story 4.0c — Evaluate benchmark without dictionary, decide disable/remove, restore zero-preprocessing promise. Blocker for all Epic 4 stories.

### Epic 4 Plan Update Required: YES

Epic 4 grows from 8 to 11 stories. The 3 foundation stories (4.0a, 4.0b, 4.0c) must execute first, before Stories 4.1-4.8.
